# Package audit — October 23, 2026

The supplied package had launch-blocking stale references. They have been fixed,
and local regression checks cover the startup chain, input validation, training
helpers, resume behavior, and report generation. This is not a claim that all
99 configurations have been trained on Sapelo2.

## Changes

| Finding | Resolution |
|---|---|
| Startup checked a private, absolute tree-dataset path while the batch template used the new packaged dataset. | Startup and the template now both use the selected project's `image_dir/labels.csv` and `image_dir/images/`. |
| Startup exported an old project variable while the batch template read `EXPERIMENT_DIR`. Invoking startup from another directory could select the wrong project. | Unified the variable to `EXPERIMENT_DIR`, canonicalized/exported it, and verified paths containing spaces. |
| Old project names remained in job names, manifest experiment IDs, fold-file paths/version labels, generated-script examples, messages, and the report's filename/title. | Updated executable references to the resize/LR naming. Manifest IDs are now `resize_lr_001`–`resize_lr_099`; default fold file is `fold_assignments.csv`. |
| Batch directives contained a personal scratch path and email address. | Removed personal settings; startup supplies project-local log paths. |
| Concrete `--csv-path`/`--photos-path` defaults made `--data-folder` ineffective. | Both overrides default to `None`; the resolver derives `labels.csv` and `images/` from the selected data folder. |
| A new random seed was chosen on every process launch, including resumes. Existing result directories could then refer to different splits. | Resolve the seed once, reuse a saved configuration/assignment seed, validate its range, and reject conflicting explicit seeds. New configurations still get random seeds. |
| Resume could reuse a directory after a dataset change when no fold was complete yet. | Compare the entire saved image/split assignment table before resuming. The comparison covers subject IDs, classes, image paths, filenames, and subsets. |
| A repeated image filename could place identical image data under different subject IDs and leak it across folds. | Reject duplicate resolved image paths and paths outside the photo directory. This does not identify duplicate image bytes under different filenames. |
| Empty labels, unreadable images, or undersized crops could fail only after GPU jobs started. | Add CPU-only `--validate-data-only`; every `start.sh --run` queues dataset preflight before its dependent GPU jobs. Header-only `labels.csv` supplies the expected schema. |
| Repeated submissions could concurrently write the same experiment outputs. | `--run` and `--reset` check for active jobs in the selected project directory before submission. |
| Module lists were duplicated in preparation and batch scripts. | Put the same pinned module stack in `load_modules.sh`; both paths source it. Batch scripts now use a login-shell shebang. |
| Literal class names such as `NA` or numeric strings could be reinterpreted during CSV reloads. | Preserve subject/class strings when loading labels, assignments, and raw-output metadata. |
| Report rows could disagree on learning rate/resize strategy without detection. | Reject mixed configuration rows; report labels also use the requested fold count. |

The original training method remains: ImageNet initialization, model-specific
input dimensions, fixed crop sizes, five outer/eight inner splits, AdamW with
zero weight decay, float32, validation-based checkpoint selection, and the
64/1 → 32/2 → 16/4 → 8/8 OOM retry schedule. Smaller micro-batches can change
batch-normalization/stochastic behavior; gradient accumulation preserves the
effective batch target, not an identical optimization trajectory.

The supplied historical workbook was moved to
`reference_results/previous_random_split_results.xlsx` **without changing its
bytes or original labels**. Historical labels inside that workbook are the only
intentional old-project references retained. It is never read by the executable
pipeline. No training results from the user's dataset were generated by this audit.

## Dataset findings

- The number of classes comes from `Species`, and the final classifier is rebuilt
  with that many outputs. There is no fixed 35-class or total-image-count limit.
  The audited package explicitly requires at least two classes.
- Each class needs at least 10 independent subjects. Every fold enforces at least
  7 training, 1 validation, and 2 test subjects per class.
- The schema requires one unique `OBJECTID` row per subject and all four
  `Photo0`–`Photo3` columns, with 1–4 populated image paths per row. There is no
  fixed number of photos per class. Extra photo columns are not consumed.
- Dog-breed classification works under the same schema. All pictures of one dog
  must share one subject row; renaming the column header is unnecessary.
- All images must be at least 960 × 960 for the supplied full manifest. Direct
  resize-only training can accept smaller images. Metrics are image-level.
- The limits on folds (5/8), crops (960/480), allowed learning rates, and supported
  model/batch combinations are enforced in code. Removing their CLI arguments
  does not remove those constraints.

## Verification

Checks ran with Python 3.11.17, PyTorch 2.1.2+cpu, torchvision 0.16.2+cpu,
NumPy 1.26.4, pandas 2.0.3, scikit-learn 1.4.2, Pillow 10.0.0, and matplotlib 3.7.2.
The packaged cluster modules use Python 3.11.3 and CUDA builds of PyTorch and
torchvision. The cluster's complete module environment was not reproduced here.

The regression suite contains 27 tests: **26 passed; one DataLoader multiprocessing
test was skipped because this environment blocks the local IPC sockets it needs**.
The suite is included in `tests/test_experiment.py`.

- Python parsing and Bash syntax checks passed for all source scripts.
- Mock-Slurm checks exercised preparation-only startup, cold/warm-cache runs,
  dependency wiring, active-job rejection, reset preservation, and preparation
  failure. No real Slurm commands were submitted.
- All eight generated batch scripts executed against a Python-command recorder.
  Their 99 commands parse successfully against the real training parser and
  cover every manifest configuration exactly once.
- Tests checked the renamed paths from an unrelated working directory and from
  a project path containing spaces, and compared all cached-weight filenames to
  the installed torchvision weight enums.
- Real torchvision transforms passed all 33 model/resize combinations. A real
  EfficientNet-B0 model with three output classes completed CPU forward,
  backward, and optimizer steps using random test weights.
- Synthetic three-class data exercised minimum group counts, missing columns,
  duplicate IDs/images, path escapes, bad images, crop limits, multiple photos
  per subject, seed boundaries, and saved assignment reuse.
- The real five-fold orchestration ran with a tiny CPU model and explicitly
  mocked CUDA availability. It wrote checkpoint, epoch/fold metrics, raw-output,
  confusion-matrix, and configuration artifacts; validated/skipped completed
  folds; and retrained only an interrupted fold. Labels included `NA` and `007`
  to exercise CSV round-tripping.
- An injected OOM verified that the retry moves from 64/1 to 32/2 while keeping
  the seed. Actual GPU out-of-memory behavior was not exercised.
- The report generator processed the smoke-test results from both a directory
  and a ZIP. Test metrics are synthetic and are not retained as experiment results.

The Sapelo2 documentation lists the selected H100 request and the pinned
PyTorch/torchvision module family:
[GPU/software](https://wiki.gacrc.uga.edu/wiki/GPU) and
[job submission](https://wiki.gacrc.uga.edu/wiki/Running_Jobs_on_Sapelo2).
Actual account permissions, module loading, network downloads of all pretrained
weights, GPU memory use, job durations, and full training remain to be verified
on Sapelo2 with a populated dataset.
